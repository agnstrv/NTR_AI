# Совместная работа
## Роли
Автор публикует рабочие и незавершённые разработки. Проверяющий — другой человек команды, который берёт проверку в Trello и испытывает решение на своём проекте. Он принимает решение о слиянии; координатор не является обязательным согласующим.
AI помогает исследовать, писать, проверять, публиковать и сливать после явного решения проверяющего. «Все права» не означает разрешение удалять исходники, переписывать чужую историю или обходить настройки доступа.

## Цикл
1. Выбрать карточку и каноническую папку. Проверить существующие ветки/PR.
2. Получить origin/main, прочитать актуальные правила. Новая независимая работа начинается от origin/main. Незавершённая чужая работа — от конкретного commit её ветки.
3. Создать work/<author>/<tool>/<job-id>; при параллельных чатах — отдельный worktree.
4. Выполнить цикл agent-harness.md. Обновлять job и handoff.
5. Просмотреть staged diff; commit + push своей ветки. Автору не обязательно сразу открывать PR: коллега может fetch ветку без PR.
6. Проверяющий отмечает себя в Trello, создаёт свою review/work ветку от опубликованного commit, запускает кейс на копии своего проекта.
7. Сохраняет report: человек, дата, исходный проверенный commit, среда, кейс, результат, ограничения, решение. Отчёт может быть следующим документационным коммитом; изменение кода после проверки требует повторной проверки изменённого поведения.
8. Для main открыть PR с точным типом принятия. Проверяющий подтверждает своему агенту решение. Агент проверяет head, diff, отчёт, CI при наличии и конфликты, затем сливает при доступных правах. Если человек не имеет права или защита блокирует, запросить действие уполномоченного участника, не обходить ограничение.
9. В Trello записать commit/PR, проверяющего, область применимости и следующий шаг. Закрывать карточку только при выполнении её критериев, а не по одному факту merge.

## Два разных принятия
| Статус инструмента | Значение |
|---|---|
| research | Исследование, решение ещё не получено |
| prototype | Есть реализация или сценарий; воспроизводимость не подтверждена |
| validated | Проверки выполнены и записаны, независимая приёмка ещё впереди |
| accepted | Другой человек испытал решение на своём проекте и принял для указанной области |

main может содержать любой из этих статусов. Для research/prototype проверяющий может принять полноту упаковки и корректность описания незавершённости. Это не переводит инструмент в accepted и не переносит карточку в «Готово к применению».
В README сохранять accepted_commit и ограничения ранее принятой версии; в job отдельно писать статус новой доработки. Новый непроверенный код не наследует accepted автоматически.
Статусы Trello сопоставлять по фактам: работа → «В разработке», передача коллеге → «Проверяем результат», accepted и выполненные критерии карточки → «Готово к применению».

## Продолжение и конфликты
При передаче указать исходную ветку и commit, следующего участника и актуальную ветку. Ветки разных авторов не являются вложенной иерархией.
Для независимой новой задачи не брать чужую незавершённую ветку. Если продолжение зависит от неё, указать зависимость в job/PR: не включать непроверенные изменения предшественника незаметно.
Параллельная работа — с распределением файлов и частей геометрии. Одна живая сцена — один управляющий агент.
Проверяющий, изменивший алгоритм/код, становится соавтором: его изменения принимает первоначальный автор или третий человек. Мелкая правка инструкции, не меняющая поведение, допускает самостоятельное принятие проверяющим.
У общей опубликованной ветки не переписывать историю. Синхронизация через merge после сохранения текущей работы. Не применять reset --hard, clean -fd или force push для «исправления» чужих изменений.

## Первое внедрение
Этот набор правил вступает в работу после проверки и merge PR. До этого тестировать из ветки PR, явно указывая её.
Пилот: два участника выгружают по одному комплекту; коллега повторяет один кейс. Зафиксировать трудности и доработать правила. Пилот не выполнен самим наличием документов.
